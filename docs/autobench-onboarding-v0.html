Autobench on the Edge Node

Autobench turns weeks of manual privacy-balancing work into a single run. You give it a pre-aggregated CSV; it computes privacy-constrained peer weights, validates every selected dimension cut, and writes an Excel report.

This is the analyst onboarding for the shared Edge Node deployment. 

What it does

The balancing logic in one minute, then we run things.

A naive peer average is easy to skew and easy to make non-compliant: one dominant player (a large issuer, a large acquirer) can exceed the privacy concentration cap in some segments, making the whole comparison unpublishable. Autobench first attempts one global weight vector across the selected cuts so that

  • privacy concentration rules are satisfied in every selected dimension cut,
  • dominant players are scaled down only where needed, and smaller players scaled up,
  • the market picture stays as close to reality as the constraints allow.

Weights are computed on one primary metric (typically an amount) and then applied to every secondary metric (fraud amount, fraud count, approved and declined counts, …) within the corresponding calculation.

compliance_strict is the default. It is strict about privacy, not about using one weight vector: when a single global solution is infeasible, it may use compliant per-dimension fallbacks. Check Weight Methods before reusing weights across cuts. Only strategic_consistency guarantees one global vector.

Two analysis modes

ModeQuestion it answersExample
Share How is activity distributed across categories, compared to peers? % of spend by CP/CNP, region, or channel
Rate How does a performance rate compare to peers? Approval rate, fraud rate (in bps)

Client vs. market

There are two ways to position the client, chosen with the Target entity field:

  • Target set — the client is separated from the market. Autobench balances the peers independently and compares the client against the adjusted benchmark, measuring over- or under-performance. This is usually the preferred setup when the client already owns its raw data.
  • Target blank (peer-only) — the whole population is balanced together and you get a market view with no target comparison.

One-time setup

The Release Operator maintains one shared runtime per node at /ads_storage/autobench. You only onboard yourself.

  1. Run the onboarding script (this is the "bootstrap command" — also safe to rerun any time your launchers misbehave): 
    /ads_storage/autobench/onboard.sh
  2. If autobench is not found afterwards, your shell has not picked up ~/.local/bin: 
    export PATH="$HOME/.local/bin:$PATH"
which autobench
which autobench-cli

Onboarding validates the shared runtime, creates your private state under /ads_storage/$USER/.autobench, and installs two thin launchers in ~/.local/bin: autobench (the terminal UI) and autobench-cli (the command line). Both use the same engine and give the same results.

If onboarding says the shared runtime is missing or invalid, stop and send the exact error to the Release Operator. Do not run install.sh or pip yourself — analysts cannot repair or replace the shared runtime.

Daily workflow

Three steps, every time.

  1. Extract your data with SQL and land the aggregated CSV in a working directory.
  2. Go to that directory and launch: 
    cd /path/to/my/work
autobench
  3. Configure and run the analysis. Outputs are written next to your data (relative paths stay relative to where you launched).

The TUI remembers safe, dataset-independent preferences such as the preset, output format, and ordinary option checkboxes. It deliberately does not restore CSV/output paths, target entities, or per-run compliance declarations. Choose the dataset and target afresh in every process; metric and dimension choices become available after the CSV is loaded. Browse… (or Ctrl+O) lists the CSV files in your current directory so you rarely need to type a path; typing one and pressing Enter also works.

Useful shortcuts: Ctrl+O browse · Ctrl+R run · Ctrl+A advanced parameters · F1 preset guide.

Prepare your CSV

Autobench expects a pre-aggregated file: one row per entity × dimension bucket (optionally × time period). Do the aggregation in SQL, not in the tool.

Every column plays one of four roles:

RoleWhat it isExamples
Entity The peer participants being balanced. One column identifies them; common names like issuer_name are detected automatically. Issuers, merchants, market participants
Dimensions Categorical columns that segment the analysis. Each selected dimension becomes a set of privacy constraints and a report sheet. CP/CNP, region, domestic vs. cross-border, channel
Metrics The measures being balanced. One primary metric drives the weights; secondary metrics receive the same weights. Amount, count, fraud amount, fraud count, approved, declined
Time Optional period column for time-aware consistency. It can also simply be treated as another dimension if that suits the analysis. year_month, ano_mes

Combined dimensions are built upstream, in SQL

If the client wants reporting by a combination of dimensions (entry mode × region, card type × channel, …), create that combined column in the source query before loading the CSV. Autobench treats it as one more dimension: 

SELECT
    issuer_name,
    year_month,
    card_type,
    channel,
    CONCAT(card_type, ' + ', channel) AS card_type_channel,
    SUM(txn_cnt) AS txn_cnt,
    SUM(amount)  AS amount
FROM source_table
GROUP BY
    issuer_name,
    year_month,
    card_type,
    channel;

The combined column enters the same optimization as the other dimensions. Autobench first tries to include it in the global vector, but a strict run may use a compliant per-dimension fallback. Confirm the final method in Weight Methods.

Rules that cause most first failures

  • Entity names are case-sensitive. Renner and renner are different entities.
  • Column names get normalized to lowercase with underscores (Card Type → card_type). Refer to them that way.
  • No nulls in the entity or metric columns. Null-heavy dimension columns cause warnings and balancing difficulties — clean them in SQL or drop the dimension.
  • Units must be consistent across all rows (same currency, same count definition).
  • You need at least 5 peers for a normal run (4 for a declared merchant-spend run). Fewer peers means no privacy rule can be satisfied.

If validation fails, fix the data — do not disable validation to force a run. A workbook produced from bad input is not a usable benchmark.

Configure a run

The TUI walks you through the same order every time. This mirrors it.

1 · Data source

Point at your CSV. The header row loads and populates every dropdown that follows.

2 · Entity

Pick the Entity ID column (defaults to issuer_name when present) and the Target entity. Leave the target blank for a peer-only market run (see Client vs. market).

3 · Analysis options

Pick a preset (see Presets), then the option checkboxes. Recommended for normal work:

  • Analyze impact (on by default) — adds distortion analysis and impact sheets so you can see what the balancing cost you.
  • Validate input (on by default) — checks the CSV before analysis and surfaces problems as warnings/errors.
  • Include calc. metrics (CSV) — enriches the balanced CSV export with calculated metrics.
  • Compare presets — optional; runs every preset and reports the impact of each. Useful when choosing a preset for a new dataset.

Output format: keep Analysis while working. An analysis workbook is internal and is not client-safe merely because its automated checks pass. Anything that leaves the analysis room must be generated as Publication (or Both); see Read the output for the exact two-stage publication gate.

For merchant projects, the same Analysis Options block also has Anonymized aggregated merchant-spend context (enables 4/35) — see Merchant projects.

4 · Analysis mode — metrics and dimensions

On the Share tab:

  • Primary metric — usually the approved amount. This is the metric the weights are optimized on.
  • Secondary metrics — fraud amount, fraud count, approved/declined counts, etc. They receive the same weights.
  • Dimensions — selected last. Every dimension you tick adds privacy constraints, so start with the cuts the client actually asked for. If balancing struggles, remove a dimension and rerun (see Troubleshooting).

The Rate tab asks instead for a total (denominator) column plus approved and/or fraud columns, with fraud reported in bps by default. For issuer fraud or chargeback runs, Total must be the clearing-spend amount: Autobench uses the selected total_col as the concentration basis and requires privacy_basis: clearing_spend. It does not infer or substitute another column.

Press Run Analysis (Ctrl+R). The log should end with Analysis completed successfully and the saved report path.

Your first run

Do this before touching project data. The shared tree ships a known-good demo file (1 target + 6 peers), so you learn the workflow without debugging your data at the same time. 

mkdir -p /ads_storage/$USER/autobench-demo
cp /ads_storage/autobench/tests/fixtures/gate_demo.csv /ads_storage/$USER/autobench-demo/
cd /ads_storage/$USER/autobench-demo

The TUI shows every choice on screen — the best way to learn what the options mean.

  1. Launch autobench, press Browse…, and pick gate_demo.csv.
  2. Set Entity ID column to issuer_name and Target entity to Target (case-sensitive).
  3. In Analysis Options: time column year_month, preset compliance_strict. Leave Analyze impact and Validate input on.
  4. On the Share tab: primary metric txn_cnt, dimensions card_type and channel.
  5. Run Analysis. The log should end with Analysis completed successfully.

Same run, one command — this is what you script once a configuration is settled.

Share analysis

autobench-cli share \
  --csv gate_demo.csv \
  --entity Target \
  --metric txn_cnt \
  --dimensions card_type channel \
  --time-col year_month \
  --preset compliance_strict \
  --output gate_demo_share.xlsx

Rate analysis (also exports a balanced CSV)

autobench-cli rate \
  --csv gate_demo.csv \
  --entity Target \
  --total-col total \
  --approved-col approved \
  --dimensions card_type channel \
  --time-col year_month \
  --preset compliance_strict \
  --export-balanced-csv \
  --output gate_demo_rate.xlsx

Check it worked

All four must be true. If any is false, go to Troubleshooting.

  • The command exited with code 0 (CLI) or the TUI log says Analysis completed successfully.
  • The output file exists in your working directory (the rate run also writes a *_balanced.csv).
  • The Summary sheet in the workbook shows Input Validation: pass.
  • The Summary sheet shows Compliance Verdict: fully_compliant.

The generated .xlsx, .csv, and benchmark_log_*.txt files are local artifacts, safe to delete, and must never be committed anywhere.

Presets

A preset is a bundled optimization strategy. Press Preset Guide (F1) in the TUI for the full descriptions, or autobench-cli config show <preset> for the exact parameters.

PresetGoalWhen to use it
compliance_strict Zero privacy violations, fail-closed. The default everywhere. Most conservative; may split into separate per-dimension weighting solutions when a single global one is infeasible.
strategic_consistency One single global weight vector across all cuts. When the weights need to be reused elsewhere (dashboards, follow-up analyses). Tolerates limited, minimized violations to keep one coherent system.
balanced_default Middle ground between compliance and practicality. General exploration. Allows small controlled deviations — acceptable thresholds need alignment with your manager before anything ships.
low_distortion Keep results near-raw by locking weights close to 1. When preserving analytical accuracy matters more than perfect balancing. Requires the accuracy-first acknowledgement.
minimal_distortion Accuracy above privacy, via very high tolerance. Same family as above, looser. Requires the accuracy-first acknowledgement.
research_exploratory Maximum flexibility for difficult datasets. Directional insight when full compliance may be impossible. Never a production output. Rarely needed.

Practical rule from onboarding: run compliance_strict first. Only move to another preset when strict is infeasible or the deliverable explicitly needs a single reusable weight vector — and record why.

Privacy rules

Automatic. Listed here so you know what the tool is doing, not so you can tune it.

The engine evaluates every concentration rule that is applicable to the emitted output. Any applicable rule that passes can authorize the numeric-policy result; the report records every evaluation and the authorizing rule or rules. The familiar baseline is 5/25: at least 5 peers, and no peer contributes more than 25% to any category-level comparison.

RuleMin peersMax concentrationNotes
5/25525%The normal starting rule
6/30630%Requires ≥3 participants at ≥7%
7/35735%Requires ≥2 at ≥15% and ≥1 at ≥8%
10/401040%Requires ≥2 at ≥20% and ≥1 at ≥10%
4/35435%Anonymized aggregated merchant spend only — requires an explicit declaration (see below)

These automated rules do not decide whether a business request is eligible for Autobench. Before loading data, the analyst must resolve digital-wallet review, dual protected entity axes, recurring-deliverable rechecks, peer-group changes, and the prohibition on top-merchant deliverables through the upstream Privacy/governance process. Autobench trusts that upstream eligibility decision; there are no CLI, TUI, YAML, or Python switches for those business decisions.

Merchant projects

Merchant benchmarking (e.g. Renner, Riachuelo) needs a specific configuration — it does not work as a plain issuer-style run. The merchant declaration is available in both the TUI and the CLI.

  1. Set the Entity ID column to your merchant column — the issuer_name default does not apply.
  2. To use the merchant rule (4/35), declare the run as anonymized aggregated merchant spend. In the TUI, under 3 · Analysis Options (below Output format), check:
    Anonymized aggregated merchant-spend context (enables 4/35)

Same declaration from the CLI:

autobench-cli share \
  --csv merchant_data.csv \
  --entity-col merchant_name \
  --entity "Client Merchant" \
  --metric amount \
  --dimensions region channel \
  --preset compliance_strict \
  --anonymized-aggregated-merchant-spend \
  --output merchant_share.xlsx

The declaration is a statement of fact about the deliverable, not a convenience switch. Only declare it when the output genuinely is anonymized, aggregated merchant spend. If in doubt, confirm the framing with Privacy before running.

Top-merchant deliverables are not eligible for Autobench. Resolve that upstream before running the tool; Autobench does not ask the analyst to self-attest this decision.

Read the output

Choose the output contract first; then open Summary and the dimension sheets.

Output modeExact meaning
analysisInternal diagnostic workbook. It may contain peer identities, detailed weights, and analysis-only sheets. Never send it to a client.
publicationClient-facing candidate. Autobench sanitizes it, validates the sanitized artifact, and writes it only if that validation passes.
bothRequests both contracts. The analysis workbook remains internal; only the separately named publication workbook is a client-facing candidate.

The publication gate has two mandatory stages

  1. Sanitization transforms the artifact. It removes or redacts analysis-only identities, detailed weights, debug content, and non-publication metadata.
  2. Publishability validation inspects that transformed artifact. It checks that the sheets, columns, and identity fields forbidden by the publication contract did not survive sanitization.

Upstream eligibility: decide before Autobench

If either stage fails, Autobench withholds the publication workbook. Passing the numerical privacy rules does not convert an analysis workbook into a publication workbook, and manual deletion of sheets is not a substitute for the publication gate.

Sheet / fileWhat it tells you
SummaryRun inputs, preset, validation result, and compliance verdict. Always check this first.
One sheet per dimensionTarget vs. balanced peers per category, with gaps and best-in-class comparisons. This is the answer to the business question.
Weight MethodsWhich weighting strategy each dimension used (Global-LP, Per-Dimension-LP, or Bayesian fallback).
Rank ChangesHow the reweighting shifted peer ranks — a distortion check.
Balanced CSVBalanced metrics for BI tools (Power BI, Tableau) or pipelines. Written with --export-balanced-csv / the TUI checkbox.
Audit packageOne zip with workbook(s), CSV, audit log, config snapshot, and validation summary. Written with --audit-package.

JSON sidecars, balanced CSVs, audit packages, and quarantined/non-publishable diagnostics are not publication-redacted unless their own validated publication contract explicitly says otherwise.

Troubleshooting

Fix the first concrete error. Most first-run failures are an exact-value mismatch.

“Entity not found”

The target entity must match the CSV exactly, including case. In the demo file the target is Target, capital T. In the TUI, pick it from the dropdown instead of typing.

“Column not found”

Column names are normalized to lowercase with underscores (Card Type becomes card_type). If unsure, load the file in the TUI and look at the headers it lists.

Null-related warnings, or balancing keeps failing

This is usually the data, not the tool. Simplify and rerun: drop the sparsest dimension, clean nulls upstream in SQL, or collapse thin categories. Get a simple configuration to succeed first, then add dimensions back one at a time.

LP infeasibility warnings or high distortion

Some market structures cannot satisfy every constraint; the engine falls back to a weaker method and reports it in Weight Methods. Use Compare presets and Analyze impact to see the trade-off. This is a data property, not a bug.

autobench: command not found 
export PATH="$HOME/.local/bin:$PATH"

Or open a new SSH session. If the command is still missing, rerun /ads_storage/autobench/onboard.sh.

Stale launcher warning, or launchers behave strangely

Rerun the onboarding script — it replaces stale launchers without deleting your config or private files:

/ads_storage/autobench/onboard.sh
Shared runtime missing or invalid

Send the exact error to the Release Operator. Analysts cannot repair or replace the shared runtime.

Output write fails

Your working directory is probably not writable. Launch from a writable directory, or point the output at /ads_storage/$USER/….
